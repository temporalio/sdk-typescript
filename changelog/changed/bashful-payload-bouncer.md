A `PayloadValidationError` thrown by the Payload Converter while converting a payload produced by Workflow code (Activity, Local Activity, Nexus Operation and Child Workflow arguments, signals to child or external Workflows, memos, user metadata, the Workflow result, and Continue-As-New arguments and memo) now fails the Workflow Task instead of the Workflow Execution, even if Workflow code catches the error, so the Workflow can make progress once the converter accepts the payload. The Workflow Task failure reports the `PayloadValidationError` itself (for the Workflow result it previously reported an `UnhandledRejectionError`). This also applies to commands issued from Signal and Update handlers: an Update whose handler hits such a failure is no longer rejected; the Workflow Task fails and the Update is retried with it. A `PayloadValidationError` thrown directly by Workflow code still fails the Workflow Execution.
This takes precedence over `WorkerOptions.workflowFailureErrorTypes` and `WorkflowDefinitionOptions.failureExceptionTypes`, even when they include `Error`: such a failure always fails the Workflow Task, including when Workflow code catches it and throws an error of a configured type instead (any resulting Workflow failure is discarded with the rest of that Workflow Task's commands). A Worker or Workflow configured to fail the Workflow Execution on any error will therefore still retry the Workflow Task in this case.
Replaying a history in which such a `PayloadValidationError` previously reached Workflow code at these call sites (where it was caught, failed the Workflow, or rejected an Update) now fails the Workflow Task if the converter still rejects the value.
